# Development and verification

The canonical product contract is [PROJECT-SPEC.md](PROJECT-SPEC.md). This guide describes the currently implemented foundation and how to test it. It is not a production installation or migration guide.

## Local test fixture

From a Linux checkout with PHP CLI (8.1 or newer), mysqli, MariaDB server/client tooling, curl, tar and unzip:

    scripts/test-integration.sh

The script downloads exact WordPress 7.1.5 and WooCommerce 11.3.1 archives by default. Override PHP_BIN, WP_VERSION and WC_VERSION for other explicit combinations; provide WP_ARCHIVE and WC_ARCHIVE to reuse the corresponding downloaded archives. The fixture checks their installed versions. It creates a private temporary WordPress installation and MariaDB data directory, starts its own socket-only server and removes that fixture on exit. It does not require an existing database or production credentials. Run as an ordinary development user. No external provider requests are needed: HTTP response fixtures intercept all adapter test requests.

The workflow exercises PHP and JavaScript syntax, actual database transactions and concurrent processes, mocked provider HTTP requests, native Abilities permissions, plugin activation/deactivation, and WordPress/WooCommerce account and payment integration. Native wp_insert_user accepts an empty email, whereas wc_create_new_customer requires a valid email. Tests cover native account creation and login, role/policy and hook denial, session qualification and revocation, linking and changing identity, email recovery checks, concurrent registration and interrupted registration. Tests also exercise native email registration followed by first mobile linking on the same user, expired native authority, optional password enrollment, native email confirmation storage guards, classic and block checkout rendering, native fallbacks, safe redirects, receipt/non-target rendering and Persian catalog loading. Full browser and staging acceptance remain separate validation items.

## Foundation boundaries

- Plugin-owned transactional tables enforce unique native user IDs and canonical mobile numbers, durable send reservations, attempt counts and short-lived proof consumption.
- Verification remains an internal service. BrowserApi exposes only the explicitly enabled, same-origin HTTPS POST WordPress AJAX account flow (action ach_wp_accounts; operations status, start, issue, complete, recovery_email and recovery_password). It requires the configured origin, X-ACh-Accounts header, and a browser-bound signed ticket backed by a Secure/HttpOnly/SameSite=Strict host-only cookie. Tickets bind purpose, native account/session context and identity revision; proof consumption remains server-side. Network identity is derived from REMOTE_ADDR, not arbitrary forwarding headers. Responses are not cacheable. Actual browser transport, proxy configuration and caching behavior require staging validation.
- The initial policy uses a 300-second code lifetime, 600-second continuation lifetime, five verification attempts and 60-second identity cooldown; hourly mobile/network/site issuance limits are 5/60/300 and daily site limit is 2000. These are development defaults, not a production traffic or financial-cost policy. Fixed-window quotas count reserved send attempts (not SMS segments or money). The settings/application slice must validate operational policy and account for provider costs and proxy/NAT topology. WordPress auth salt rotation invalidates outstanding proof/hash-derived quota keys; coordinate it with account recovery and provider operations.
- The normalization check accepts Iranian mobile number families (90, 91, 92, 93, 99 except public-trunk 9950), not fixed or service families. It does not assert that a number is allocated or active. Reference: [CRA numbering plan published by ITU, 2025-04-20](https://www.itu.int/dms_pub/itu-t/oth/02/02/T02020000660032PDFE.pdf). Maintain this check as numbering classifications evolve. Kavenegar can convert a fixed-line verification request into a voice call, so this distinction matters.
- The provider registry implements only the two approved providers. Multisite activation is blocked in this development build until site/network identity ownership is resolved. The initial schema is still unreleased; earlier development fixtures are not an upgrade contract. State-preserving activation is tested; release upgrades, deactivation/recovery safety and uninstall/purge require their own validation. Do not install this draft on a live site.

## Native account and session flow

- The approved policy is in PROJECT-SPEC.md. Use native WordPress users, roles, sessions and cookie APIs, and WooCommerce account lifecycle hooks. Phone-only registration requires explicit plugin permission plus applicable native registration policy. It creates a unique generated login, no synthetic email, and no claimed guest orders. A durable unique reservation precedes native user creation. If creation is interrupted or ambiguous, retain the reservation for reconciliation; do not retry native user creation blindly.
- An identity revision binds a consumed OTP to the exact native session. Checkout qualification lasts no longer than that session; logout, revocation, deletion or changed identity invalidates qualification. Changing an established mobile identity requires recent qualifying proof (600 seconds, a development default) or native credential reauthentication plus the new number's OTP. First linking on an ordinary account may instead use a recent valid native login session (same freshness window); stale native sessions require reauthentication. Linking does not create a new account or rotate its identity into another user. The development reauthentication budget is ten attempts per account per hour.
- Account eligibility is fail-closed for elevated/custom roles and unrecognized effective capabilities. Preserve native authentication/account-policy hooks and the native password path. Compatibility with actual installed security extensions requires staging acceptance.
- Native email/username login and site-native email registration remain available independently of the plugin's mobile registration toggle. Use WooCommerce My Account registration when enabled, or native WordPress registration where allowed. If registration is allowed only in WooCommerce checkout, the gated checkout supports mobile signup under that policy; it does not invent an additional email signup route. A native email login/registration never satisfies required mobile proof on its own.
- For phone-created accounts, optional recovery email uses native WordPress profile confirmation; the pending address is not stored as an account credential until confirmed. The enrollment requires fresh mobile proof, uses a 24-hour link lifetime and five requests per account/hour (initial defaults), and preserves billing email independently. Optional native password enrollment also requires fresh proof and at least 15 characters without composition rules. Existing native email accounts retain native recovery policy. Full HTTP confirmation, deactivation/recovery lifecycle, controlled interrupted-registration reconciliation and lost-credential recovery need separate acceptance.
- For isolated development only, ach_wp_accounts_auth_enabled, ach_wp_accounts_allow_registration and ach_wp_accounts_checkout_required are separate opt-in options (off by default); ach_wp_accounts_provider supplies the selected registry configuration. No production operator settings/validation UI is available yet. An enabled flag is not proof of provider readiness or end-to-end usability.

## Messaging contracts

Official sources:
- [Kavenegar REST](https://kavenegar.com/rest.html): Verify Lookup, SMS Send, Account Info, response and message status tables, template configuration.
- [Melipayamak pattern sending](https://www.melipayamak.com/api/sendbybasenumber2/) and [ordinary SMS](https://www.melipayamak.com/api/sendsimplesms2/): HTTPS REST endpoints, ordered pattern arguments separated by semicolons, response codes and provider receipt identifiers.

Kavenegar uses an API key and a named template/token set, or an explicitly selected ordinary message. Melipayamak uses username/API key in the provider credential fields and an approved body ID with ordered values, or ordinary text. The internal registry accepts a default configuration and explicit overrides for login/link/step-up purposes. No automatic fallback, retry or live request happens during plugin activation, discovery, or tests.

Transport uses WordPress HTTP, HTTPS certificate verification, no redirects, bounded response size and timeout. Treat known request rejection or terminal non-delivery differently from acceptance and uncertain outcomes; keep machine status/reference only. An accepted provider receipt does not prove SMS delivery. The test connection operations do not send SMS. Actual credentials, response shapes, templates, delivery and provider-side retry/fallback settings need authorized staging verification. In particular ensure that Kavenegar templates and provider account options do not unexpectedly enable voice fallback or automatic duplicate sends. Do not enable HTTP request tracing that records OTPs, provider credentials or credential-bearing URLs; WordPress third-party HTTP hooks must also preserve these secrets.

## Checkout integration evidence

Core guards target the classic checkout validation and order-processed hooks, Store API checkout POST routes and late payment boundaries, and native order-pay after its nonce/order ownership checks. Order-pay uses a scoped available-gateway filter and a native notice instead of throwing outside the WooCommerce payment try/catch. When the checkout requirement is enabled, qualification is evaluated on the current native session, not the billing phone or a client flag. When disabled, these guards do not interfere.

The fixture tests actual Store API negative dispatch for checkout and checkout-by-ID, classic validation and order-processed hooks, unrelated route behavior, and actual WC_Form_Handler::pay_action with a fixture gateway: unqualified sessions do not reach process_payment; a qualified session does. Frontend intercepts the classic checkout shortcode and Checkout Blocks before rendering payment controls on the gated customer checkout. The shared form uses the same account flow in ordinary wp-login, My Account, profile, checkout and shortcode/popup. It leaves native login/reset/reauthentication paths and receipts intact. Native fallback uses local return destinations; checkout and native return responses are marked non-cacheable. The front end never grants payment authorization. Assets are scoped to relevant pages/form rendering.

A preliminary local Chromium check on the working tree observed the classic guest gate, native My Account email signup and return to checkout, first-mobile linking UI without a repeated password, OTP request UI with mock provider and Persian-digit input, and block checkout gate at a 390px viewport without horizontal overflow. It did not complete OTP submission in the browser; the positive identity/session and renderer transitions are covered by PHP integration tests. This is not full successful classic or Store API checkout, cart persistence, HTTP recovery confirmation, full RTL browser acceptance or proof of coverage for installed express-payment plugins, alternate routes, redirects and asynchronous callbacks. Validate these paths on staging.

## Localization

The shared form and current customer messages use the ach-wp-accounts text domain. The Persian PO and compiled MO are in languages/. After modifying the catalog, compile it with:

    msgfmt --check -o languages/ach-wp-accounts-fa_IR.mo languages/ach-wp-accounts-fa_IR.po

The integration fixture loads the native Persian catalog and checks translated form rendering and input directions. Future operator UI requires its own translation coverage.


## Native discovery

On WordPress versions exposing the Abilities API, ach-wp-accounts/status is registered as a read-only ability requiring manage_options. It returns the stored and expected schema versions, implemented provider capabilities and the current availability of authentication and checkout policy. No provider credentials, identity data or proof material are included. The status capability reports configuration/schema and WooCommerce availability, not table integrity, provider connectivity, browser usability or production readiness. Native execution permission checks are tested; actual MCP/Bridge discovery remains a staging acceptance item.
