# Development and verification

The canonical product contract is [PROJECT-SPEC.md](PROJECT-SPEC.md). This guide describes the implemented candidate, reproducible fixtures and maintenance contracts. Actual deployment and historical data import require separate site-specific acceptance.

## Local test fixture

From a Linux checkout with PHP CLI (8.1 or newer), mysqli, MariaDB server/client tooling, Python 3, curl, tar and unzip:

    scripts/test-integration.sh

The script downloads exact WordPress 7.1.5 and WooCommerce 11.3.1 archives by default. Override PHP_BIN, WP_VERSION and WC_VERSION for other explicit combinations; provide WP_ARCHIVE and WC_ARCHIVE to reuse the corresponding downloaded archives. The fixture checks their installed versions. It creates a private temporary WordPress installation and MariaDB data directory, starts its own socket-only server and removes that fixture on exit. It does not require an existing database or production credentials. Run as an ordinary development user. No external provider requests are needed: HTTP response fixtures intercept adapter requests, and mail/payment effects use isolated fixtures. Optionally supply WP_CLI_PHAR with an independently verified local WP-CLI PHAR to exercise the actual local commands (the main fixture does not download WP-CLI).

The workflow exercises PHP and JavaScript syntax, actual database transactions and concurrent processes, mocked provider HTTP requests, native Abilities permissions, plugin activation/deactivation, and WordPress/WooCommerce account and payment integration. Native wp_insert_user accepts an empty email, whereas wc_create_new_customer requires a valid email. Tests cover native account creation and login, role/policy and hook denial, session qualification and revocation, linking and changing identity, email recovery checks, concurrent registration and interrupted registration. Tests also exercise native email registration followed by first mobile linking on the same user, expired native authority, optional password enrollment, native email confirmation storage guards, classic and block checkout rendering, native fallbacks, safe redirects, receipt/non-target rendering and Persian catalog loading. Full browser and staging acceptance remain separate validation items.

## Foundation boundaries

- Plugin-owned transactional tables enforce unique native user IDs and canonical mobile numbers, durable send reservations, attempt counts and short-lived proof consumption.
- Verification remains an internal service. BrowserApi exposes only the explicitly enabled, same-origin HTTPS POST WordPress AJAX account flow (action ach_wp_accounts; operations status, start, issue, complete, recovery_email and recovery_password). It requires the configured origin, X-ACh-Accounts header, and a browser-bound signed ticket backed by a Secure/HttpOnly/SameSite=Strict host-only cookie. Tickets bind purpose, native account/session context and identity revision; proof consumption remains server-side. Network identity is derived from REMOTE_ADDR, not arbitrary forwarding headers. Responses are not cacheable. Actual browser transport, proxy configuration and caching behavior require staging validation.
- The initial policy uses a 300-second code lifetime, 600-second continuation lifetime, five verification attempts per challenge and 60-second identity cooldown; hourly mobile/network/site issuance limits are 5/60/300 and daily site limit is 2000. A separate mobile verification-attempt budget defaults to 25 per UTC hour (the previous default issuance budget times five attempts), remains shared across renewed challenges, and can be configured from 1 to 100. The 600-second maximum OTP lifetime and independent attempt limiting are informed by [NIST SP 800-63B-4, out-of-band authentication and rate limiting](https://pages.nist.gov/800-63-4/sp800-63b.html); the fixed-hour throttles are local policy, not a claim of NIST conformity. These are development defaults, not a production traffic or financial-cost policy. Fixed-window quotas count reserved send attempts (not SMS segments or money). The shared settings service validates configurable issuance and verification policy; provider cost, real throughput and proxy/NAT topology still require staging acceptance. WordPress auth salt rotation invalidates outstanding proof/hash-derived quota keys; coordinate it with account recovery and provider operations.
- The normalization check accepts Iranian mobile number families (90, 91, 92, 93, 99 except public-trunk 9950), not fixed or service families. It does not assert that a number is allocated or active. Reference: [CRA numbering plan published by ITU, 2025-04-20](https://www.itu.int/dms_pub/itu-t/oth/02/02/T02020000660032PDFE.pdf). Maintain this check as numbering classifications evolve. Kavenegar can convert a fixed-line verification request into a voice call, so this distinction matters.
- The provider registry implements only the two approved providers. Multisite activation remains blocked until site/network identity ownership is resolved. Schema 1 is still the initial unreleased schema; no transition from disposable pre-release development fixtures is promised. Installation/resume, unsupported newer schema rejection, state-preserving activation, deactivation/reactivation proof revocation, same-schema native ZIP upgrade and deliberate purge are covered in isolated tests. A future schema version needs its own explicit transition and upgrade/rollback acceptance. Do not install this draft on a live site.

## Native account and session flow

- The approved policy is in PROJECT-SPEC.md. Use native WordPress users, roles, sessions and cookie APIs, and WooCommerce account lifecycle hooks. Phone-only registration requires explicit plugin permission plus applicable native registration policy. It creates a unique generated login, no synthetic email, and no claimed guest orders. A durable unique reservation precedes native user creation. If creation is interrupted or ambiguous, retain the reservation for reconciliation; do not retry native user creation blindly.
- An identity revision binds a consumed OTP to the exact native session. Checkout qualification lasts no longer than that session; logout, revocation, deletion or changed identity invalidates qualification. Native login/logout discard the browser-flow cookie, and the lifecycle epoch invalidates outstanding plugin proof authority on explicit deactivation/reactivation without destroying native sessions. Changing an established mobile identity requires recent qualifying proof (600 seconds, a development default) or native credential reauthentication plus the new number's OTP. First linking on an ordinary account may instead use a recent valid native login session (same freshness window); stale native sessions require reauthentication. Linking does not create a new account or rotate its identity into another user. The development reauthentication budget is ten attempts per account per hour.
- Account eligibility is fail-closed for elevated/custom roles and unrecognized effective capabilities. Preserve native authentication/account-policy hooks and the native password path. Compatibility with actual installed security extensions requires staging acceptance.
- Native email/username login and site-native email registration remain available independently of the plugin's mobile registration toggle. Use WooCommerce My Account registration when enabled, or native WordPress registration where allowed. If registration is allowed only in WooCommerce checkout, the gated checkout supports mobile signup under that policy; it does not invent an additional email signup route. A native email login/registration never satisfies required mobile proof on its own.
- For phone-created accounts, optional recovery email requires fresh mobile proof and sends a 24-hour confirmation link to the native profile controller, using five requests per account/hour (initial defaults). Store only the token digest with the pending/previous email, identity revision, epoch and expiry in plugin-owned storage. Confirmation requires the same authenticated native account; consume the exact record before the guarded native email update. Do not use a core pending-email record that could be consumed after plugin deactivation. The existing native email remains authoritative until confirmation; billing email stays independent. Optional native password enrollment requires fresh proof and at least 15 characters without composition rules. Existing native email accounts retain native recovery policy. Tests execute the actual profile controller with native session cookies in an isolated PHP process; full HTTPS/browser delivery and redirect acceptance still belong to staging. Loss of all trusted credentials requires controlled manual recovery outside automated reassignment.
- The unreleased development flags and provider option have been replaced by the single non-autoloaded ach_wp_accounts_settings snapshot. Authentication, phone signup and mandatory checkout are independent explicit booleans (off by default); a checkout requirement cannot be enabled without authentication and a valid saved provider. Site-native email policy remains independent. The native admin UI uses this same snapshot; this is not a live-site configuration guide. An enabled flag is not proof of provider connectivity or end-to-end usability.

## Messaging contracts

Official sources:
- [Kavenegar REST](https://kavenegar.com/rest.html): Verify Lookup, SMS Send, Account Info, response and message status tables, template configuration.
- [Melipayamak pattern sending](https://www.melipayamak.com/api/sendbybasenumber2/) and [ordinary SMS](https://www.melipayamak.com/api/sendsimplesms2/): HTTPS REST endpoints, ordered pattern arguments separated by semicolons, response codes and provider receipt identifiers.

Kavenegar uses an API key and a named template/token set, or an explicitly selected ordinary message. Melipayamak uses username/API key in the provider credential fields and an approved body ID with ordered values, or ordinary text. The internal registry accepts a default configuration and explicit overrides for login/link/step-up purposes. No automatic fallback, retry or live request happens during plugin activation, discovery, or tests.

Transport uses WordPress HTTP, HTTPS certificate verification, no redirects, bounded response size and timeout. Treat known request rejection or terminal non-delivery differently from acceptance and uncertain outcomes; keep machine status/reference only. An accepted provider receipt does not prove SMS delivery. The test connection operations do not send SMS. Actual credentials, response shapes, templates, delivery and provider-side retry/fallback settings need authorized staging verification. In particular ensure that Kavenegar templates and provider account options do not unexpectedly enable voice fallback or automatic duplicate sends. Do not enable HTTP request tracing that records OTPs, provider credentials or credential-bearing URLs; WordPress third-party HTTP hooks must also preserve these secrets.

## Checkout integration evidence

Core guards target the classic checkout validation and order-processed hooks, Store API checkout POST routes and late payment boundaries, and native order-pay after its nonce/order ownership checks. Order-pay uses a scoped available-gateway filter and a native notice instead of throwing outside the WooCommerce payment try/catch. When the checkout requirement is enabled, qualification is evaluated on the current native session, not the billing phone or a client flag. When disabled, these guards do not interfere.

The fixture tests actual Store API negative dispatch for checkout and checkout-by-ID, classic validation and order-processed hooks, unrelated route behavior, and actual WC_Form_Handler::pay_action with a fixture gateway: unqualified sessions do not reach process_payment; a qualified session does. Frontend intercepts the classic checkout shortcode and Checkout Blocks before rendering payment controls on the gated customer checkout. The shared form uses the same account flow in ordinary wp-login, My Account, profile, checkout and shortcode/popup. It leaves native login/reset/reauthentication paths and receipts intact. Native fallback uses local return destinations; checkout and native return responses are marked non-cacheable. The front end never grants payment authorization. Assets are scoped to relevant pages/form rendering.

A preliminary local Chromium check on the working tree observed the classic guest gate, native My Account email signup and return to checkout, first-mobile linking UI without a repeated password, OTP request UI with mock provider and Persian-digit input, and block checkout gate at a 390px viewport without horizontal overflow. It did not complete OTP submission in the browser; the positive identity/session and renderer transitions are covered by PHP integration tests. The separate native purchase fixture now executes WC_Checkout::process_checkout and actual Store API checkout dispatch with native nonces and a successful isolated payment gateway. It checks rejection without a qualifying mobile session, cart preservation on rejection, successful paid order ownership/amount and billing-email isolation from the phone-only account. WordPress-only registration and login are also tested before WooCommerce activation. These are real core execution paths, not a live charge or proof of target gateway/express integrations, cross-login browser cart restoration, full browser OTP/HTTP recovery, theme/cache coverage, alternate routes or asynchronous callbacks. Validate those paths on staging.

The shared form, customer and operator messages, and updater errors use the ach-wp-accounts text domain. The Persian PO and compiled MO are in languages/. After modifying the catalog, compile it with:

    msgfmt --check -o languages/ach-wp-accounts-fa_IR.mo languages/ach-wp-accounts-fa_IR.po

The integration fixture loads the native Persian catalog and checks translated form rendering and input directions. Operator controls, messages and updater errors also have a Persian catalog; only the compiled runtime catalog is distributed.


## Shared operator service and native discovery

The Settings service owns configuration, pure provider validation and the redacted operator projection. The saved snapshot contains selected provider, separate saved configurations for the actual providers, common default pattern/text route and optional per-purpose overrides, authentication/registration/checkout flags, verification policy and diagnostic retention. Provider request construction is shared by validation and real dispatch; saving settings does not make a network call. Switching providers preserves the other saved configuration. Credentials are stored in a non-autoloaded site option, are not registered in WP REST settings, and are never returned by the operator projection. Access to the database, backups, query debugging and third-party HTTP hooks remains privileged; protect those storage/transport surfaces. No encryption-at-rest claim is made. The internal credential-write path is used by the nonce-protected native admin adapter; machine-facing settings updates cannot provide or delete credentials.

A single expected-revision compare-and-swap protects the saved option against simultaneous admin/AI writes (native update_option lacks an expected-value precondition). The operation uses a guarded SQL update of this plugin-owned option only and invalidates the option cache. Stale saves return settings_conflict; the caller must reload current state and explicitly reconcile. Concurrent runtime requests already in flight may use their previously loaded configuration. Persistent external object cache behavior remains a staging acceptance item. Validation rejects a checkout requirement without authentication, invalid saved providers, and unsupported enable-time site/origin/schema states. No implicit network test or activation side effect occurs on save. Policy changes apply to new issuance; existing challenge expiry and resend timestamps remain recorded.

On WordPress versions exposing the Abilities API, the following operations use explicit schemas and execution-level checks. General operations require manage_options; account identity migration/reconciliation additionally require edit_users and applicable edit_user permission:
- ach-wp-accounts/status and settings-read: installed and expected schema, provider capabilities, configuration/credential presence, flags, environment/cleanup readiness; not a live connectivity or full health assertion.
- settings-update: non-secret patch plus exact current revision.
- provider-connection: saved provider connection test without SMS, with a bounded diagnostic result (mutating diagnostic evidence, not a read-only operation).
- provider-test-send: explicit confirmation, selected saved provider/purpose, recipient and unique request ID. One potentially billable message; same issuance quotas/cooldown as customer traffic. Exact replay is safe within 24-hour challenge retention and the same native operator/request/provider context; no automatic retry. A test challenge has no code hash, cannot be verified/consumed, and cannot authenticate an account.
- diagnostics-query: authorized keyset pagination, bounded page size (1–100), category/provider/state/purpose/date/correlation filters. UTC epoch timestamps, machine-readable code/reference, duration, masked recipient tail, verification state and retry safety. Accepted is provider acceptance, not delivered; pending/uncertain never implies safe automatic resend.

- registration-pending: read redacted reservation classification and matching native user evidence. registration-reconcile: explicit confirmation of an exact reservation and matching ordinary native user; finish the interrupted binding only. registration-release: explicitly confirmed destructive release only when native creation never began and no matching account exists.
- migration-preview and migration-execute: the exact reviewed Digits mapping contract below, site-bound digest, bounded page, explicit confirmation for apply.

Diagnostic send history is projected from authoritative challenge rows, with a minimal non-secret snapshot after a send completes for retention beyond OTP cleanup. Live rows take precedence; a missing snapshot or interrupted send remains visible while the challenge exists. No raw phone, OTP, proof hashes, credentials, provider bodies or URLs are included in the query projection. Connection tests and selected exceptional account failures have bounded events; common bad-code attempts are represented by existing challenge counters, not an event for every request. Diagnostic history defaults to 24 hours, configurable from 1 to 168 hours, with scheduled bounded cleanup. Raw challenge storage retains its separate 24-hour lifecycle for proof and replay correctness; shortening diagnostic retention hides and expires diagnostic history independently. A longer history cannot reconstruct verification counters after challenge expiry. No external telemetry service.

The isolated fixture exercises actual concurrent CAS (four processes, one successful write), credential preservation/forbidden writes, both provider configurations and switching without HTTP, native Ability schema/permission checks, mocked connection and test sends, shared budgets, exact replay, safe test-only records, uncertain/pending fallback, redacted diagnostic pagination/retention and renewed-challenge attempt limits. The native admin adapter exposes one ACh WP Accounts menu with General, SMS & verification, and Diagnostics tabs. It uses scoped styles/scripts, native forms, manage_options, action-bound nonces, exact settings revision, and safe local POST/redirect/GET for successful settings changes. Provider credential fields are blank/write-only and disabled on HTTP, with an execution-level HTTPS check when writing credentials. Blank keeps the previous value; explicit confirmed configuration removal is separate. Provider selection does not change inactive configurations. Test operations use a saved configuration snapshot; admin passes its revision, and Abilities may optionally pass the same expected revision. A stale revision refuses the test before contacting the provider. No hidden autosave or automatic send. Validation failures retain non-secret values, and an old draft cannot silently acquire the current revision. Tests cover admin nonce/capability, safe rendering and accessible unique IDs, both provider configurations, stale/error drafts, masked receipt/history, test-send idempotency, policy and retention. A local real WordPress admin browser check with the official Persian core language pack verified saving provider config, blank credential fields, selecting a provider, mock connection receipt and focus, invalid message draft preservation, saving the three general flags, and diagnostic filtering/empty state. The document stayed within 390px in RTL; only the diagnostics table scrolled internally. Native keyboard submission worked; Playwright pointer stability timed out and one separate session ended with uncertain completion. Recovered the fixture state before retesting; no real SMS was sent. Browser test-send, full LTR/RTL/theme matrix and actual Bridge/MCP/provider acceptance remain separate staging items.


## Lifecycle, reconciliation and privacy

The initial schema (1) is committed only after the explicit installation transition, actual transactional table/column/index checks, initial settings, lifecycle epoch and cleanup schedule succeed. A pending transition may resume on a later admin (not AJAX), cron or WP-CLI request under a site-scoped database advisory lock. Normal customer traffic does not execute DDL. An unsupported newer schema is not silently downgraded; status exposes a safe readiness/error code, and OTP/session authority is refused. On reactivation an already-installed schema is validated rather than silently reconstructing missing identity data. Explicit activation/deactivation changes the authority epoch; a silent native same-schema package update retains it. Future schema increments must provide explicit transitions; incrementing a constant alone cannot declare success.

Native creation holds a per-mobile reservation lock. Before calling native user creation, mark the unique reservation as started durably. Reconciliation must inspect the reserved login, exact registration marker, current native account and permissions. Finish only an existing matching ordinary account after explicit confirmation; never retry an ambiguous native creation or transfer a reservation to an arbitrary account. Release only an unstarted reservation without matching account evidence. A started reservation with missing/conflicting evidence remains reserved for investigation. Use the native registration Abilities rather than introducing an unapproved new admin workflow.

Native Tools > Export/Erase Personal Data callbacks resolve the native account by email. Export includes the current verified identity and attributable pending recovery/session and current-binding challenge metadata recorded at issuance, without OTPs, token hashes or credential material. Local WP-CLI also resolves a phone-only account by native user ID after operator authorization. Review identity provenance before export; a reused number never transfers challenge history from its previous identity revision; unattributable challenges and archives expire by their normal retention. Erasure removes temporary proofs/pending email and current-binding challenge data and linked evidence, using the recorded and current exact binding revision. Unattributable masked archives and aggregate rate buckets expire by their retention contracts. A surviving account's verified mobile is retained if deleting it could prevent recovery (no usable native email reset path). Return retained-item information rather than silently lock out the user. Native credentials, accounts, orders and billing/contact records are not erased by the plugin; native user deletion invokes plugin identity cleanup. Storage failures require reconciliation rather than blind reassignment.

Local commands (only on the explicitly authorized site, with a native administrator selected through WP-CLI's global --user option):

    wp --user=<administrator> ach-accounts privacy-export --user-id=<native-user-id> --page=1
    wp --user=<administrator> ach-accounts privacy-erase --user-id=<native-user-id> --confirm=erase-account-data

Keep export output private. Repeat export pages until done. Ordinary deactivation or WordPress plugin deletion preserves plugin-owned records; removing plugin files may make mobile-only login unavailable and mandatory checkout policy cannot be enforced by an inactive plugin. Before deactivation/removal, establish alternative account access and coordinate checkout behavior.

Deliberate purge is separate: verify a restorable backup, alternative access for all affected accounts, disable mobile authentication and checkout requirement, quiesce in-flight requests, and obtain separate destructive-operation authorization. The command requires manage_options, edit_users, delete_plugins and explicit confirmation:

    wp --user=<administrator> ach-accounts purge --confirm=purge-accounts-data

It deactivates the exact plugin and removes its own six tables, settings/schema/epoch/error options, specific recovery/registration metadata, update cache and cleanup events. It never deletes native users, orders or billing data. The operation cannot be undone without a backup; phone-only login/verification mappings will be lost. If interrupted, leave the plugin inactive and inspect the actual state before a controlled resume or restore. No automatic purge occurs during update or ordinary deletion.

## Reviewed historical identity migration

Do not infer verification from Digits phone metadata, billing phone, a matching email or a unique-looking phone. Inspect the actual legacy version/data and authoritative verification history first. Prepare a complete reviewed mapping for the migration scope, including all conflicting/unverified candidate rows needed for duplicate detection. Keep the manifest and its underlying evidence private; do not put real phones in the public repository, general logs or unnecessary remote requests. The operator explicitly attests to the historical proof and user-ID mapping. An example with fictional values (not migration evidence):

    {
      "evidence": "synthetic example only; replace with actual reviewed provenance",
      "rows": [
        {"user_id": 123, "mobile": "09120000001", "verified": true, "verified_at": 1760000000},
        {"user_id": 456, "mobile": "09120000002", "verified": false}
      ]
    }

verified_at is an optional known UTC epoch; absence means unknown (0), not a newly invented verification date. The full mapping is normalized and checked for duplicate user IDs and phones on every page, including conflicts across pages and with unverified rows. Preview is read-only; it reports row index, native user ID, masked mobile tail, classification, digest, total and next_offset. Digest binds the exact normalized mapping and provenance to the site/database identity. Only confirmed ready rows can be imported; the write checks actual current native eligibility and unique bindings and never overwrites or creates users. Replay on the same mapping reports an existing exact binding. Keep the full manifest unchanged; restart preview after modifying evidence or rows, and reconcile write_unconfirmed or conflicting rows rather than retrying an altered plan.

For a local private manifest file:

    wp --user=<administrator> ach-accounts migration-preview /private/reviewed-mapping.json --offset=0 --limit=50
    wp --user=<administrator> ach-accounts migration-execute /private/reviewed-mapping.json --offset=0 --limit=50 --digest=<reviewed-digest> --confirm=import-reviewed-identities

Inspect every preview page and obtain explicit site-specific import approval first. Then apply pages using next_offset until complete; verify post-import counts/mappings and preservation of the legacy account, order, balance and role state. Resolve unsupported/unknown/conflicting candidates by relinking or an approved manual recovery process. The native Abilities expose the same service, without local path access. No legacy plugin activation or data removal is performed. The isolated tests use a synthetic reviewed manifest; actual Digits source extraction, proof provenance, complete mapping, rollout/rollback and target-store acceptance are not established by those tests.

## Release packaging and native updates

Distribution uses the public AChWorks/ach-wp-accounts GitHub repository. The active plugin's Update URI and WordPress native update hook register the latest complete stable GitHub Release; WordPress owns scheduling, update notices, user permissions, filesystem installation and normal update preferences. No GitHub token, separate update service or forced automatic update. Sites must be able to reach GitHub release/API endpoints and use the native WordPress update system. This hook is loaded when the plugin is active; for a deactivated copy use the official release ZIP manually if needed. A failed lookup does not invent a version. Details use escaped release notes.

Prepare a stable version header X.Y.Z on the reviewed release candidate, retain Requires PHP: 8.1, complete exact-candidate checks and obtain the required integration/release authorization. Build from a clean reviewed checkout (or exported exact reviewed source) with:

    python3 scripts/build-release.py --tested-wp <verified-version>

This prepares dist/ach-wp-accounts.zip and dist/ach-wp-accounts-release.json without publishing. Omit --tested-wp if not established. The ZIP has one ach-wp-accounts/ root and the entry file, PHP includes, runtime assets, compiled localization and GPL license. Only the current flat runtime layout/file types are included; extend the packaging contract and test when new runtime directories or file types are actually introduced. Source PO, docs, tests, scripts, repository configuration and temporary files are excluded. Build twice and verify identical bytes, manifest digest/size, header version and PHP requirement; the fixture tests do this and exercise a real Plugin_Upgrader install of a newer same-schema package. Never ship an automatically generated GitHub source archive.

Publish the exact reviewed artifacts together in a GitHub stable Release tagged vX.Y.Z. The ZIP and manifest names must be ach-wp-accounts.zip and ach-wp-accounts-release.json. Create a draft until both assets are uploaded and checked, then publish only with authorization. Do not replace a published tag or asset; correct a defective release with a new version. The update manifest contains slug, version, filename, SHA-256, byte size and PHP/WP compatibility. The updater checks the release/tag/asset/manifest consistency, verifies GitHub's asset digest when present, checks compatibility, refreshes the exact tag before downloading, rejects changed advertised digest and verifies downloaded bytes before native extraction. This is integrity checking against the trusted public release, not an independent publisher signature. Keep GitHub publishing access protected. Test the first actual stable release's native update discovery and asset download on staging; no public release has yet been issued. A same-schema test is not proof of safe future schema migrations or rollback. The initial schema installation and interruption recovery are tested; validate each actual future version transition, backup and recovery plan before release.
