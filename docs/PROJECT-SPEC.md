# ACh WP Accounts — Project Specification

Status: Owner-approved product direction, 2026-11-27, updated by Issue #4 on 2026-11-28. Architecture is a design contract, not a claim of implemented or tested capabilities.

## Purpose and ownership

Provide a maintainable, lightweight WordPress account extension, initially replacing Digits and its combined login/registration add-on for Blinko. Customers should be able to enter or create their existing WordPress account using a verified mobile number without choosing between login and registration first. Operators should configure messaging and diagnose problems without editing plugin code, enabling WP_DEBUG, or depending on proprietary encoded source. Future account, profile, authentication and identity-verification capabilities must remain possible without speculative implementation today.

Display name: ACh WP Accounts. Repository: AChWorks/ach-wp-accounts. Plugin slug, directory, entry point basename and text domain: ach-wp-accounts. Author: ACh; Author URI: https://ach.li/. Canonical project-level truth is this document. Issues own active work; source, tests, checks and releases own implementation/validation/delivery truth.

## Scope and non-goals

Initial release:
- Unified mobile number + SMS OTP login/registration, ordinary native password login fallback and safe account recovery; registration only where permitted by the site's applicable WordPress or WooCommerce account policy. Existing account resolution occurs after proof. Collect only necessary profile fields. Independent public email-registration and ordinary-customer password sign-in policies supplement applicable native settings. Keep native password recovery and privileged access, supported machine authentication and authorized provisioning; do not add a competing email-registration system.
- Verified mobile identity management, safe linking/change with current-account authorization and verification of new number; existing WordPress account/profile integration. Native user/customer directories expose authoritative mobile and verification state/date and search complete or partial normalized mobile numbers alongside native search, permissions, filters and pagination, without mirrored identity metadata.
- Native wp-login.php integration, WooCommerce My Account, checkout, shortcode/inline and optional popup from the same reusable form and application operations. Do not replace unrelated core login actions (logout, password reset, interim login, reauthentication, etc.) or native account ownership.
- Kavenegar and Melipayamak with verification/pattern and ordinary text modes, connection/test-send controls and meaningful diagnostics.
- Settings, native machine-readable Abilities, protected diagnostics, and previewable/restartable Digits migration.
- English source and translatable UI; complete fa_IR translation, RTL/LTR, accessibility and responsive interaction.

Out of scope until separately approved: passkeys, social login, email OTP, advanced MFA/session management, extensive profile builder, marketing campaigns, SMS automation beyond account needs, external identity/KYC checks, national-ID/mobile matching, card/account ownership checks, banking/payment processing, standalone identity service, new central Foundation. Future verification integrations are plausible but do not justify collecting national IDs, card numbers or other KYC evidence now. Preserve an explicit identity/verification boundary and provider separation; introduce purpose-specific evidence and policies only when a real feature requires them. Never treat mobile possession as evidence of national-ID or payment-instrument ownership. Future identity/attribute verification providers belong to the verification domain, not the SMS transport contract; no generic KYC schema or provider framework is required now.

## Architecture and platform

One independently released modular WordPress PHP plugin (modular monolith); no required service, ionCube, Node runtime, Redis, external application database or build tools on production hosting. Use WordPress APIs and supported WooCommerce extension points. Scope data, configuration and authorization to the correct site/account context; determine multisite support explicitly rather than claiming untested network behavior. The owner-approved minimum PHP version is 8.1 (plugin header, release metadata, build validation and CI must agree). The compatibility baseline must include Blinko's observed PHP 8.1 and WordPress 7.1.5 / WooCommerce 11.3.1, and modern supported PHP/WP/WC combinations; these observed target versions are initial acceptance inputs, not hardcoded maximums or claims of tested support. The minimum WordPress core is 6.3, which supplies the native password-reset authorization API; the WordPress-only baseline is separate from WooCommerce and its own compatibility requirements. Keep native headers, runtime guards, package validation, release manifest and tested matrix aligned. Feature-detect optional capabilities. Do not force an upgrade of the production site's PHP or stack as part of this project.

Responsibility boundaries (not a mandatory file/class/module count):
- Account authentication/application operations: resolve verified identity, enforce account and site policy, create or authenticate the native user, manage the existing session and return typed outcomes.
- Identity/profile: own unique mobile-to-user binding and possession state, normalization, uniqueness, linking/change and migration rules. WordPress remains authoritative for user IDs, credentials, roles, sessions and profile data; WooCommerce remains authoritative for customers, billing/contact data, cart, orders and payments.
- Verification: own purpose-bound OTP challenge lifecycle, atomic issuance/consumption and abuse policy, independent of presentation and SMS transport.
- Messaging: small provider contract and registry, capability discovery, per-provider configuration/validation and structured send/test results. Provider adapters handle transport, never issue sessions, authorize operations or terminate an HTTP/UI response.
- Integrations: thin WP login, WooCommerce, frontend, admin, API/Abilities adapters call shared operations. Reuse standard WP hooks, REST facilities, translations, HTTP client and native auth/session semantics; avoid bypassing existing authorization/security hooks.
- Diagnostics: structured bounded events and actionable failure context for authorized operators; one source of operational truth shared by admin and AI.

Prefer straightforward local functions/classes and explicit dependencies. Do not create empty future interfaces, generic workflow engines, shared services, or speculative extensibility frameworks. Use a provider contract because two providers are already required. Maintain clear boundaries so future methods or verification evidence can be added without rewriting current phone OTP. Reconsider extraction only with demonstrated reuse. No Foundation dependency: AChrix is a Go application foundation, not a fit for WordPress PHP; ACh Pay Manager owns bank SMS/payment verification, not customer authentication. Source review of Adev OTP Login 1.2.1 and Nomreh 0.12.0 (292dd66e9ffce38867bb9ace728f62db27d6f7ac) found fundamental auth, identity and concurrency defects; use architectural lessons, not a fork or unreviewed code.

## Authentication, identity and verification contracts

- Normalize international/local Iranian mobile formats and Persian/Arabic digits to a single canonical identity; validate using actual numbering/provider contracts. Keep display formatting separate. No arbitrary assumption that an email, username, billing_phone or last digits alone prove identity.
- A verified login phone belongs to at most one native account. Enforce at storage/concurrency boundary; never silently pick the first ambiguous match. Billing/contact phone is not an authentication credential. Linking, changing or migrating identity must not enable account takeover. Phone-only registration must account for WordPress/WooCommerce email requirements, unique usernames, native recovery and role assignment without silently claiming an unverified email or creating a duplicate account. Do not generate placeholder emails. Where native site registration policy permits, create phone-only accounts with no account email. Billing contact remains separate; respect the existing checkout-required fields. Do not claim an unverified account email as a recovery credential or merge accounts by it. Add a recovery email only after confirmation from the authenticated native account. Apply the same optional recovery policy to imported phone-only accounts, with fresh mobile proof for enrollment, without changing registration provenance or existing native credentials. Use native mail/profile/account APIs with an expiring, single-use plugin-owned pending record bound to the identity revision and lifecycle epoch; never leave a core pending change that can bypass plugin proof when inactive. Do not expose unnecessary account-existence information before proof.
- Generate OTP with cryptographically secure randomness; recommend six digits by default, subject to validated provider/policy requirements. Protect stored codes with keyed hashing; constant-time comparison where applicable. Bind proof to normalized identity, purpose, challenge and appropriate session/flow; enforce server-side expiry, bounded attempts and atomic single-use semantics. Registration continuation is proof-bound, short-lived and single-use. Never trust a hidden input, client-side flag, IP-only transient or arbitrary caller-supplied user ID as proof. Protect state-changing requests and session establishment against CSRF/login-CSRF and replay; validate redirect destinations; use native secure cookies and session lifecycle. Page caches, shared proxies and separate browser tabs must not transfer proof or account state between users.
- Rate-limit issuance and verification proportionately by relevant identity, client/network and aggregate spend/traffic. Reserve/record attempts before the external effect where needed; handle concurrent requests, cache eviction, resend races and failures without duplicate effects or unbounded verification attempts. Use configurable, validated defaults where operators genuinely vary; choose actual security/operational limits during implementation. Do not impose arbitrary lockouts or unrelated CAPTCHA requirements.
- Native password login/recovery remains available as appropriate; privileged accounts retain a safe native access path when SMS is unavailable. OTP must not bypass role/capability policies, existing account controls or security extensions. Owner-approved policy (2026-11-27): permit SMS-only sign-in for ordinary customer/subscriber-class accounts; evaluate effective capabilities and deny elevated/custom roles by default. Preserve native password and existing security controls for privileged accounts. Checkout step-up is independent of SMS-only eligibility. Linking/changing mobile requires fresh proof of existing account authority (current qualifying verified mobile proof or native credential where appropriate), and OTP for the new mobile. An ordinary guest with an existing account and no mobile identity may prove its native credential and an unbound mobile OTP in a single controlled first-link recovery flow, without a password-only session, duplicate user or email-based automatic linking. Changing the password or identity while recovery is pending invalidates that flow. For first linking only, an ordinary account with a recent valid native login session may use that fresh native authority without re-entering a password; otherwise require native reauthentication. Show that the number is being attached to the existing account. Changing an established mobile identity still requires recent mobile proof or native credential reauthentication. Invalidate proof for the previous identity and prevent conflicting concurrent assignments. If all trusted credentials are lost, require controlled manual recovery, not automatic account reassignment.
- Use durable, indexed, minimal plugin-owned storage only where atomic uniqueness, proof, rate accounting or bounded events require it; prefer native APIs otherwise. Do not rely on non-atomic transient read/modify/write for security-critical invariants. Avoid long DB transactions over provider I/O. Use versioned migrations with explicit transitions, verified storage prerequisites and a commit marker only after success, UTC expiry/event timestamps, site-local display, bounded cleanup/progress. Reject unsupported newer schemas rather than downgrade. Explicit activation/deactivation revokes plugin proof authority without destroying native users or sessions. Support WordPress privacy export/erasure with deliberate retention and preserve native accounts. Provide protected local ID-based privacy operations for phone-only accounts; report retained identity/recovery data when removal would lock out a surviving account. Never attribute historical records by masked phone fragments.
- A timeout or provider response loss is not a proven send failure. Classify definite failure, accepted send and uncertain outcome; preserve correlation and provider identifiers when available; avoid blind duplicate send/failover. Safe user-directed resend respects cooldown and spend policy.

## WooCommerce checkout — mandatory acceptance contract

Blinko requires the verified-mobile checkout policy. It is configurable at site level. Issue #4 supersedes the earlier checkout form-replacement design: retain complete native Classic Checkout and Checkout Blocks, including customer fields, cart, totals, coupons, payment options and native validation. Start mobile verification on an actual payment attempt, inline on the same page without reloading or replacing checkout. Require a native authenticated account and qualifying current-session mobile proof before payment; use the entered checkout mobile when provided and require it to match the authenticated identity. Do not replace an established identity from billing data. An authenticated account without an identity can first-link; a stale session with an identity steps up by OTP. A guest may authenticate or register under applicable site policy; a guest with an existing unbound account can prove native credentials and OTP rather than create a duplicate. Billing contact remains independent. Preserve valid session/cart, refresh native checkout/Store API nonce and customer context, recalculate through WooCommerce, and only continue the native payment action when order inputs, gateway and totals have not changed. Otherwise require deliberate review/reconfirmation. Never repeat payment automatically on an uncertain outcome. Do not send OTP unnecessarily for a currently qualifying session. Logout/session revocation, identity change and proof expiration invalidate qualification. Existing order-pay retains historical contact information; enforce current-session proof and native order authority.

Enforce before actual payment initiation on supported Classic Checkout, Checkout Blocks/Store API, and relevant customer-initiated order-pay/retry and express/accelerated-payment paths where present; direct requests or manipulated frontend flags must not bypass the gate. Preserve supported checkout flows and test actual gateway/extension contracts before claiming coverage. Use WC APIs and supported hooks with verified server-side user/identity/session state. Do not intercept unrelated gateway webhooks/callbacks, existing payment completion, admin order management, or WC REST integrations outside this customer checkout policy. Preserve native WooCommerce ordering, HPOS compatibility, cart/session and payment ownership; do not recreate order processing. Clear, actionable unavailable-provider state and safe native admin access; do not silently allow an unverified shopper through on SMS failure. Verify actual active Blinko checkout surfaces and payment plugins before rollout, including redirect and returning-customer behavior.

## Messaging provider contract

Initial providers: Kavenegar (API key; Verify Lookup with template name and provider-supported token values; ordinary SMS) and Melipayamak (supported credential method; pattern/body ID with provider-defined parameter ordering; ordinary SMS). Use current official API documentation and live/sandbox evidence to settle exact endpoint, authentication, escaping, success/error/status and retry semantics. Configuration should support provider capabilities, purpose-to-template selection with sensible shared default, ordered/named variables as appropriate and text fallback mode chosen explicitly (not automatic duplicate sends). Keep actual OTP generation/validation out of transport. Expose connection status, deliberate test-send, accepted/failed/uncertain status, provider reference, error category and duration. Provider secrets are write-only or masked in administration/AI, never in logs or repository; document storage, rotation, access and masking. No unnecessary dependencies or raw arbitrary HTTP proxy.

## UX and localization

Accepted direction: one clean mobile-first login/register form, no mandatory separate tabs; phone input, request code, then code entry and continue. Mask target number after send, allow edit/back, paste and mobile OTP autofill, accessible labels/focus/keyboard and visible send/verify/error/retry/resend status. Use native site font/colors where feasible and minimal optional logo/color styling, scoped styles and scripts only on relevant pages. Use one accessible code input or equivalent accessible implementation; do not force a specific multi-cell widget. Existing users continue, new users see only required fields after proof. Keep native email/username and password login, and native email registration when enabled, discoverable as a secondary path. The owner approved this shared mobile-first design on 2026-11-27, including optional recovery password/email in the profile and mobile verification. Issue #4 replaces the pre-controls gate with inline verification at payment attempt, while retaining server enforcement. Own the ordinary guest wp-login and WooCommerce My Account login/registration documents with one responsive minimal shell, optional native methods according to policy, site identity and no theme header/footer/sidebar or duplicate native forms. Preserve native privileged, reset, logout, reauthentication and special paths. No forced redirects to hardcoded my-account slug, no global template takeover, no cacheable personalized proof/nonce/state. Design for desktop/mobile, English/Persian, RTL mixed-direction phone/OTP LTR and normalized digit input. Owner approval of exact user-facing design/behavior before implementation where it materially changes accepted direction; prototype and test real integration states rather than treating mockups as proof.

Owner-approved administration direction (2026-11-27): one native wp-admin entry, three peer tabs (General, SMS & verification, Diagnostics), a concise configuration/readiness summary, independent active-provider selection and saved provider configurations, write-only credentials, optional purpose overrides and advanced settings disclosed only when needed. Use explicit save/test actions, distinguish provider acceptance from delivery, show localized inline results with usable correlation/reference details, and preserve non-secret invalid drafts without silently overwriting a newer revision. Native styling, scoped assets, responsive LTR/RTL, keyboard access and readable mixed-direction identifiers; future migration UI only when its actual workflow is accepted.

English identifiers, comments, technical docs and source UI strings; use WordPress i18n with text domain ach-wp-accounts, translations and plural forms, no hardcoded Persian-only source strings or remote font dependency. Complete Persian translation and test locale/rendering.

## AI, administration and observability

Expose relevant native WordPress Abilities (when supported; normal UI remains usable without MCP/Bridge) with discovery metadata, explicit schemas, read-only/mutation annotations, precise permission callbacks, native capability/role checks, meaningful errors and safe pagination. Integrate through existing MCP Adapter/WP AI Bridge, not a new server. Planned operations: status, non-secret settings read/update, providers/capabilities, provider connection test, explicit authorized test send, diagnostics query, migration preview and confirmed execution. Validate inputs and authorization at execution; no ability to read OTPs/secrets or mint arbitrary customer sessions/bypass proof. Apply site authorization and protected access; do not invent an AI-specific privilege path. Shared UI/Ability operations have equivalent semantics. Persist a coherent settings revision, preserve unrelated provider configuration and reject stale concurrent saves. Configuration validation is pure; connection tests and explicit potentially billable test sends are separate actions. Test messages do not grant authentication proof, use the shared send budget and have bounded request replay protection. Non-secret AI settings updates never read or write provider credentials; credential entry/rotation/removal belongs to protected native administration. Use native registered API/hooks for appropriate extensions; version public contracts deliberately.

Diagnostics should work without WP_DEBUG and without publicly web-accessible logs. Structured events include UTC timestamp, stage/category/level, operation/correlation ID, provider, response status/error code, duration, retry safety and relevant bounded context. Distinguish accepted send vs actual delivery, definite failure vs uncertainty, invalid proof vs provider problems. Protect OTPs, API credentials, passwords and full sensitive payloads by targeted redaction, least privilege and retention; preserve useful provider cause without leaking URLs containing API keys. Operator views and AI use scoped filters/pagination/retention controls. No log-of-every-request or telemetry service by default.

## Migration, lifecycle and validation

Before migrating, inspect actual existing data/meta keys, normalization and provenance (including possible digits_phone / digits_countrycode; do not assume they are sufficient), users, references, duplicate/conflicting numbers and old form integrations, with aggregate/non-sensitive evidence. Dry-run first; preserve user IDs, accounts, orders, balances, roles and data; never auto-merge accounts or treat unverified billing values as trusted proof. Owner-approved revised policy (2026-11-28, superseding the historical-proof prerequisite): import explicitly reviewed, uncontested Digits mobile-to-existing-account mappings for eligible ordinary users even if historical verification is unknown. This establishes the mapping only, never possession; imported verification time is zero until the first fresh successful OTP for the same binding. At the separately approved site cutover revoke old sessions of the migrated ordinary customers so they sign in again; retain privileged/native access and existing payment completion. Native email/password sign-in stays available, but checkout requires fresh mobile session proof. Conflicting or excluded mappings require controlled resolution; do not use raw billing data or automatic account reassignment. Do not treat billing contact as verified identity or merge users. Idempotent resumable bounded migration over an explicitly reviewed, site-bound mapping containing authoritative evidence and all relevant conflicting candidates; support on-demand source=digits preview/apply directly from the installed plugin using the observed matching primary/country/local Digits keys, or a complete private manifest for exceptional mappings. No raw phone-list transfer, separate extractor installation or Digits runtime dependency is necessary for the direct path; incomplete/ambiguous source must remain visible and be reconciled rather than silently omitted; recheck uniqueness at apply and never overwrite an existing binding. Verify results, establish recovery and rollback, leave legacy data intact until separately authorized. Reconcile interrupted native account creation only against exact durable reservation/native account evidence; release only reservations known not to have started native creation. No production access/configuration changes until approved; validate actual replacement before removing old plugins.

Use native plugin lifecycle, state-preserving updates, safe recovery and standard ZIP without production build tool requirements. Ordinary deactivation/removal preserves data; deliberate purge is a separate authorized local operation after backup, alternative access, disabled auth/checkout policy and quiescence. Do not add migration/reconciliation UI beyond the accepted design without approval; use protected native Abilities and local WP-CLI for the current operational contracts. Owner-approved distribution: public GitHub repository and stable Release assets, native WordPress Plugins/Updates discovery and update installation, no GitHub credentials required on the site. Publish the same runtime-only installable ach-wp-accounts.zip for manual and native updating, plus its version/compatibility/integrity manifest as a separate release asset; never offer the GitHub source archive. Only plugin runtime files, required assets and compiled translations, and distribution license belong in the ZIP. Exclude development docs, tests, CI/build scripts, repository metadata, source translation catalogs, temporary files and secrets. Validate package layout, exact version, WordPress 6.3 and PHP 8.1 minimums and integrity before publication. Do not offer draft/prerelease or incomplete releases to native update checks. Use the native updater and release metadata, not a parallel custom installation or forced auto-update workflow. Use versioned release identity, checks and independent review of exact candidate before integration/release as required. No deployment or release assumed by recording architecture.

Acceptance evidence for initial release: unit tests for normalization, policy, OTP/provider parsing; real supported DB concurrent issue/verify/consume/identity uniqueness, rate/spend and migration tests; WP native login, recovery, existing/new customer, profile change, authorization negatives and deactivation/update; WooCommerce Classic and Blocks/Store API payment gate and order-pay, cart restoration, existing payment callbacks and password step-up; real/sandbox authorized provider template/test-send for each and response-loss/retry handling; browser E2E for LTR/RTL desktop/mobile, cache/CDN/object-cache and representative themes; API/Abilities schema/permissions/secret redaction/error evidence; standard installable package and upgrade/rollback tests. Use scoped CI during development, full risk-relevant exact-candidate checks before review. Verify available Blinko-like staging. Owner-approved release sequencing (2026-11-28): finish available isolated and staging checks, package and independently review the first installable release; external provider delivery, unavailable site-specific browser/integration checks and actual Blinko cutover validation may follow publication, but remain explicit operational gates before enabling the affected live authentication/checkout paths. Production acceptance and live sends/changes require separate authorization. No test or release claim until supported by evidence.
